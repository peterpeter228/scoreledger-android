# 验收测试计划

## 测试分层
1. 纯Kotlin core：原始分解析、状态、加权汇总、比较门禁、权益数量。
2. 独立Python契约：JSON结构和跨引用/异常导入。与Kotlin实际导入器共用fixtures，不能永久拿Python替代安卓导入测试。
3. Room仪器化：父子事务、外键、编辑、删除、导入回滚、migration。
4. Compose/设备：录入、返回、旋转、键盘、大字体、深色、无GMS、文件选择/分享。
5. 商业：真实测试商品购买/恢复/撤销。必须在渠道测试环境运行。

## 数据样本
全为虚构昵称和记录，不使用用户实际孩子数据。fixtures里有有效与空备份；reference测试在内存变异生成非法输入。
规模测试另生成20孩子/100科目/10,000考试/100,000成绩上限；注意每次最多30科，不让样本自相矛盾。
长中文/全角数字/0分/满分变更/缺考/未录入/跨孩子同名科目/同日考试/闰日都需覆盖。

## 设备矩阵
模拟器API26、30、36；实际用户安卓设备优先；另至少一台无GMS和一台有GMS设备。
系统厂商/版本、RAM、键盘、字体缩放、方向写证据，不能用“安卓已测”泛化。
若本环境无模拟器/真机，状态NOT_RUN，绝不把截图原型当执行证据。

## P0失败定义
丢失已提交记录、串孩子、0与缺失混淆、统计计算错误、导入覆盖失败不能回滚、购买未确认即解锁、
基础导出被权益锁、敏感数据外发、发布密钥泄露，任一出现都不得商业发布。

## 手工故障注入
- 保存按钮连点10次；只出现一个UUID；进程在事务前/中/后被杀的行为分别验证。
- 导出目标存储写满/取消/URI撤销；不能报成功，原库不变。
- 恢复前在内存校验后故意破坏文件/中断写库；只能旧库或完整新库，不能混合。
- 备份恢复到新安装后逐表计数与统计比较；重复恢复不翻倍。
- 退款/无网络/切换账号；旧数据始终可带走。

## 证据格式
每个用例标not_run/pass/fail/blocked，附设备、日期、版本、命令、日志、截图或步骤；
issue编号回链，修复后重复原case与相邻case。未执行数量必须明确，不能只写“全部通过”。

## 每次改动的实际验收门禁（2026-10-17 起）

适用于此后每次修改功能、修复缺陷或新增功能。测试是开发交付的一部分，不能以“请用户试试看”替代。已有历史测试只对原提交、APK 和明确范围有效，不自动覆盖新改动。

### 1. 先写本次覆盖范围
- 列出改动点、受影响入口/数据/相邻流程，对应既有验收用例；没有现成用例时补充可复现用例及明确预期。
- 至少覆盖正常闭环、边界/非法输入、失败提示与数据不变性、取消/返回/重复操作，以及相关重建、进程重启、持久化恢复。确实不适用的场景逐项说明原因，不默默跳过。
- 涉及数据/schema/升级时验证真实读写与迁移；同 APK 的 install -r 保留不等于不同版本升级。涉及 PDF/备份时核对实际文件内容、记录数/统计/范围与完整性，而非只看到成功提示。
- 按改动风险执行相关既有回归，尤其孩子隔离、0/缺失/缺考区分、保存幂等、统计、事务回滚及已有数据可导出。系统兼容性改动按设备矩阵验证，不用单一 API 概括所有安卓设备。

### 2. 用待交付 APK 实际操作
1. 从本次源码构建 APK，记录完整 commit、构建变体、版本、包名、APK SHA-256 和构建来源。安装并启动该 APK，核实正在运行的包与产物对应。
2. 在 Android 模拟器或已授权真机上，通过真实界面点击、输入、选择、确认/取消等完成受影响的用户流程；可采用人工操作或设备端 Compose/UI 自动化，但不得只直接调用仓储/API 后声称用户操作已通过。
3. 对每一步关键输出作断言，核对界面结果及实际数据/文件；保存后重新进入或重启核实持久化，失败/取消后核实旧数据和草稿符合预期。记录预期与实际，不以“不崩溃”代替正确性。
4. 执行所需单元/契约/仪器化、lint 和构建检查作为补充，再完成相关流程回归。发现失败先修复，再对最终 APK 重跑失败用例和受影响回归；测试后又改代码或换产物，不能沿用原通过结论。

### 3. 证据与边界
每个用例记录：
- 用例 ID、功能/改动点、前置条件、虚构测试数据说明、操作步骤、预期结果、实际结果；
- PASS / FAIL / BLOCKED / NOT_RUN，执行时间、执行方式、失败原因和复测结果；
- 源码完整 commit、APK SHA-256、构建变体/版本/包名、构建 run ID/链接（如适用）；测试 APK 不同来源时单独记录；
- 模拟器镜像或真机型号、Android/API、方向/字体/键盘等相关配置；
- 可定位的日志、断言结果、关键步骤和最终状态截图；文件导出/数据测试附实际内容校验结果，不能仅附页面截图。

证据仅使用虚构数据，遵守 AGENTS 的隐私与凭据限制。安装/启动证据、自动化报告和人工复核各自标明范围；构建成功、静态审查、单元测试通过、页面能打开或截了图，都不足以单独完成本门禁。

Mock、隔离宿主、测试文件提供方和沙盒支付只证明其实际覆盖的范围。真实 DocumentsUI/外部提供方、真实第三方集成、渠道支付必须有对应环境的端到端证据；没有则分别记未验证，不得由替身结果冒充。不得为补测试擅自付费、发布、扩大权限或使用真实孩子数据。

### 4. 交付判定
- 本次改动全部必需实际验收与相关回归通过，证据可追溯，才可将该功能标 VERIFIED，并按已完成向用户交付。
- 任一关键测试失败、缺失、未运行或环境受阻，保持 BLOCKED / IMPLEMENTED_UNVERIFIED；报告已测范围、具体缺口、影响及下一步，不能以“编译通过”“内测包”或“等待用户反馈”绕过门禁。
- 可以提供明确标为未验收的进展/诊断材料，但不能将其包装成已完成、可放心使用的功能交付。与本次范围无关的历史缺口继续单列，不抹掉也不假称补测完成。
- 用户手机/OEM、TalkBack、真实外部提供方、最大规模性能、不同版本升级、支付/商店验证按实际证据分别判定；模拟器功能验收通过不覆盖这些边界。
- 功能正确性验收、视觉/布局检查、用户对美观和易用性的认可分别记录。功能测试通过不自动等于设计满意；视觉好看或用户认可也不能替代功能测试。

### 5. 本次仅规则文档更新
本规则更新不修改应用、UI、技术栈、测试脚本或工作流，不创建新功能验收结论、不重发 APK、不发布版本。核对文档一致性、相对链接及仅文档差异即可；历史产物和已有测试结论维持原边界。
